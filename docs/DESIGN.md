# McPair · 麦麦配

**从"猜你喜欢"到"算给你看"——一个可解释的多目标用餐决策系统**

> 一局定生死的地方在于：绝大多数参赛项目在让大模型"凭感觉"报套餐，而 McPair 让大模型只做翻译，把算钱、选品、用券交给确定性求解器，任何数字都必须有 MCP 工具出处。

---

## 0. 一句话

你说一句"随便"，它在**当前门店真实在售菜单**上枚举近万种搭配，做多目标帕累托优化，用 `calculate-price` 校准真实到手价，最后给你三套方案——并告诉你为什么不是另外 9973 种。

## 1. 问题定义：推荐器 vs 决策系统

现有 100+ 参赛项目，99% 属于「推荐器」范式：

```
用户描述需求 → LLM 组合几个商品 → LLM 报一个价格
```

这个范式的三个致命问题：

| 问题 | 后果 |
|---|---|
| 报出的价格没校验 | 加购物车后金额对不上，用户信任瞬间归零 |
| 选品不落在真实门店 SKU 上 | 推荐了已停售/该店没有的商品 |
| 券是"能用就用"而非"最优用" | 实则没花掉最划算的那张券，甚至凑单凑亏了 |

McPair 属于「决策系统」范式：

```
自然语言 → 结构化约束 → 约束求解 → 真实价格校准 → 反事实解释 → 执行
             ↑ 可复现        ↑ 可测试      ↑ 有出处      ↑ 可追问
```

**核心主张：LLM 不参与算钱。** 这不是技术洁癖，是可解释性与可信度的前提。任何一个数字都能被追溯到某次 tool 调用。

## 3. 五引擎架构

不做"一个大 prompt"，做**五个职责单一、可独立测试的引擎**。

### 3.1 TasteEngine · 品味引擎

**目标**：把点餐史变成一个可计算的向量，而不是一段文案。

输入 `order-list` 全量历史，输出 8 维品味指纹 `t ∈ [0,1]^8`：

| 维度 | 计算方式 |
|---|---|
| `protein_chicken` / `protein_beef` / `protein_fish` | 按商品类目加权计数（近 3 单权重 ×1.5，随时间指数衰减） |
| `spice_tolerance` | 麦辣/香辣类占比 |
| `fried_tendency` | 炸物 SKU 占比 |
| `sweet_tendency` | 甜品/冰淇淋出现频率 |
| `drink_pref` | 可乐 / 零度 / 咖啡 / 茶 / 无饮品 |
| `portion_habit` | 单点 vs 三件套 vs 加大 |
| `price_band` | 客单价的中位数与四分位距 |
| `temporal_rhythm` | 下单时段的分布（工作日午/晚/深夜/周末） |

**关键设计——置信度**。8 笔订单的画像不可靠，必须显式标注：

```
画像置信度：0.42（样本 8 笔，建议积累到 15 笔）
```

低置信度时，画像只作为"软加权"，不作为硬约束。这个细节是专业度的分水岭——大部分项目会信誓旦旦地说"你是鸡肉党"，McPair 会说"我猜你是鸡肉党，但有 58% 的可能我错了"。

LLM 在这一层的唯一职责：把向量翻译成人话（"鸡肉党 / 必配中薯 / 中杯可乐 / 8 单 0 单牛肉"）。

### 3.2 SolverEngine · 求解引擎

**形式化**：

```
决策变量  x_i ∈ {0,1,2,...}   每类 SKU 的件数；套餐饮品/小食的替换选择
硬约束    price(x) ≤ budget
          kcal(x) ≤ kcal_cap
          allergen(x) ∩ user_allergy = ∅
          x ⊆ store_available_skus(storeCode, orderType)
          count(x) = party_size
软目标    f(x) = [ −price,  −|kcal − kcal_target|,  +protein,
                  +coupon_utilization,  +cos(t, taste(x)) ]
```

**求解策略**（分层剪枝，避免组合爆炸）：

1. 以"主餐"为外层枚举（约 40 个候选）
2. 每个主餐下，小食 + 饮品降维成二维背包 DP
3. 加购项用贪心边际收益补齐
4. 候选集控制在 1e4 量级
5. 非支配排序得到帕累托前沿

**三代表解**：前沿上的**膝点**（性价比拐点）+ 价格端 + 体验端。这比"直接取最优"有用——真实决策里人需要的是"不同取舍下的最优"，不是唯一的数学最优。

**多人模式（Squad）**：这是真正的学术富矿。多人偏好冲突本质是社会选择问题：

- 每个成员有偏好效用 `u_i(x)`
- 用**最大最小后悔**（egalitarian）或**比例公平** `Σ log u_i` 求解
- 输出每个人"让了一步什么"——这个可视化极有传播力

榜单里做拼单的只有 13★，且只做"数量累加"，没人处理偏好冲突。

> **实现状态（2026-10-17 更新）**：已落地为 `src/squad_engine.py`。
> 最终选用的聚合目标是 max-min（罗尔斯差异原则），并用**边际满意度增益**做分配
> —— 这一条比目标函数更关键：聚合再正确，分配规则错了也白搭。
> 比例公平（`Σ log u_i`）作为备选留在本轮之外，原因是它会让「某人 0.3 分」被
> 对数惩罚放大，叙事上不如「保证最不满意的人」直观。
> 实验见 `eval/squad_benchmark.py`：21 个场景中 19 个公平解 = 效率解。

### 3.3 CouponEngine · 券引擎

最被低估的一层。券不是"能用就用"：

- **互斥关系**：多张券是否可叠加
- **叠加顺序**：券 vs 套餐折扣，谁先算
- **凑单收益判断**：为使券生效而凑单，"凑单成本 < 券面额"时才是正收益，否则是**负收益陷阱**
- **机会成本**：今天用掉这张券，明天同类活动就用不了

输出三部分：最优用券方案、放弃的券及其原因、凑单的边际收益曲线。

### 3.4 ExplainEngine · 解释引擎

**反事实解释**（Counterfactual）：不只解释"为什么是 A"，更解释"怎样才能得到 B"。

```
预算 +4 元 → 可以升级到双层脆鸡堡（+120 kcal，蛋白 +9g）
放弃中薯改小薯 → 省 4.5 元，且正好让 9.9 元券生效
```

**淘汰理由排序**：把被淘汰的方案按"损失最小"排序，输出 Top 3。这是产品最有记忆点的部分，也是最容易被截图传播的部分。

**决策溯源**：每条推荐都能展开成一条链路——命中哪个画像维度、用了哪张券、价格来自哪次 `calculate-price` 调用。

### 3.5 GuardEngine · 护栏引擎

- **过敏原一票否决**：花生/麸质/乳制品，绝不进入候选集
- **价格漂移检测**：本地估算 vs `calculate-price` 返回值不一致时，以真实值为准并触发重排，同时记录漂移日志
- **限流保护**：令牌桶 600 req/min（MCP 硬限制），`query-meals` 缓存 10 min
- **幻觉防护**：任何未在 tool 返回中出现过的 SKU 或价格，直接丢弃
- **降级路径**：MCP 不可用时切 fixture 回放，产品仍可完整演示

## 5. 输出协议：渐进披露

绝不一次性倒出 800 字。三层结构：

**第一层 · 结论**（3 秒读完）
一句话画像命中 + 三档方案卡（价格 / 热量 / 蛋白 / 券）

**第二层 · 理由**（愿意看的人看）
为什么这三套 + 被淘汰的 Top 3 及原因

**第三层 · 数据**（较真的人看）
营养明细、价格构成、券规则溯源、决策链路

```
mcd-meal-pairing/
├── SKILL.md                  ← 智能体执行指令（Skill 的核心）
├── README.md                 赛事必需
├── CONTEST_DECLARATION.md    赛事必需（官方原文，不可改）
├── MCP_INTEGRATION.md        赛事必需
├── workbuddy.md              联动奖励必需
├── docs/DESIGN.md            本文件
├── scripts/pair.py           唯一计算入口（stdin JSON → stdout JSON）
├── src/
│   ├── ingest.py             接入层：拍平 MCP 返回、周边过滤、角色推断
│   ├── classify.py           名称 → 角色 / 蛋白 / 辣度
│   ├── data.py               目录与营养解析（别名归一、套餐构成推断）
│   ├── taste_engine.py       品味指纹
│   ├── solver_engine.py      组合优化 + 帕累托
│   ├── coupon_engine.py      券博弈
│   ├── explain_engine.py     反事实解释
│   ├── squad_engine.py       拼单 max-min
│   ├── guard_engine.py       护栏
│   └── view.py               输出结构
├── fixtures/                 真实接口截面（--demo 用，无 token 可跑）
├── eval/
│   ├── benchmark.py          40 场景基线对比 + 4 组消融
│   └── squad_benchmark.py    21 场拼单公平性
└── tests/                    56 个单测
```

**关键工程决策**：

| 决策 | 理由 |
|---|---|
| 求解器纯 Python，不依赖 LLM | 可复现、可单测、零 token 成本 |
| `scripts/pair.py --demo` 用固化数据 | 评委和路人**无需 token 即可验证**安装是否正确 |
| 接入层字段名容错但**不猜内容** | 对不上的写进 `issues`，不静默填默认值 |
| 所有价格必须来自 tool 返回值 | 杜绝幻觉，可审计 |
| 单测覆盖求解器边界 | 预算为 0、全员过敏、门店无在售、脚本崩溃等 |

## 7. 评估体系

这是把"作品"变成"研究"的分界线。大多数参赛项目没有评估章节。

**Benchmark（已实现）**：40 个场景（预算 × 热量上限 × 忌口 × 饮品约束）。

| 指标 | 定义 | 实测 |
|---|---|---|
| 可行率 | 硬约束全部满足的场景占比 | 100% |
| 热量贴合 | 实际热量与目标热量的贴合度 | 0.78（基线最高 0.71） |
| 主餐口味契合 | 主餐与画像的匹配度 | 0.55 |
| 券利用率 | 真正用上券的场景数 | 16/40（基线全部为 0） |

**消融实验（已实现，4 组）**：分别关掉品味引擎、券引擎、营养约束，观察指标变化。
关掉品味引擎后主餐口味契合从 0.55 掉到 0.05——这直接证明了画像的必要性。

**拼单公平性（已实现）**：21 个多人场景，对比「最大化总分」与「max-min」。
结论是 19/21 个场景两者重合，只在预算紧到必须有人让步时才分离——
如实记录，不美化。

| 日期 | 实际完成 |
|---|---|
| 10/17 | MCP 打通并采集真实数据 → 五引擎 + Squad → 56 个单测 → 接入层重构为 Skill 形态 |
| 10/18 | 冻结功能，只打磨文档与传播素材 |
| 10/19–24 | Star 积累期：README 精修、社区传播 |
| 10/25 | 缓冲，补 `workbuddy.md`，核对赛事要求 |

**一个教训**：最初把项目做成了带 Web 界面的独立产品，后来确认赛事要的是 **Skill**——
一个交给智能体执行的技能包，不是一个用户自己打开的网站。
于是删掉 Web 层，把全部计算收敛到 `scripts/pair.py` 这一个确定性入口，
让智能体只负责「听懂」和「渲染」。这个纠正让项目形态与赛题真正对齐。
